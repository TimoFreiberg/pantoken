# Bazel policy

Bazel is an additive, explicitly non-authoritative foundation. Cargo remains authoritative for Rust and pnpm remains authoritative for JavaScript. The policy is intentionally narrow so the POC can be maintained without implying a release migration.

## Pins and ownership

The supported inputs are Bazel **8.7.0** (`.bazelversion`), rules_rust **0.71.3** and rules_pkg **1.2.0** (`MODULE.bazel`), and Rust **1.97.1**, edition **2024** (`rust-toolchain.toml` and the Rust bzlmod extension). Update these together: edit the source pin, run the relevant direct ecosystem checks, repin crates with `CARGO_BAZEL_REPIN=1 bazel sync --only=crates`, review `MODULE.bazel`/generated state, then run `just bazel-policy-check`, Bazel queries/builds/tests, Cargo, and pnpm checks. Roll back by reverting the pin and generated dependency diff as one change.

`MODULE.bazel.lock` is generated by Bazel crate-universe resolution and remains intentionally untracked because the existing 2.8 MB snapshot exceeds the repository's jj snapshot limit. Its omission is a known promotion blocker, not permission to use unpinned dependencies.

## Supported platforms

Development and CI hosts are macOS arm64/x86_64 and Linux x86_64. Initial targets are the host Rust targets and an unsigned, host-independent headless archive. Windows hosts and native Windows packaging are unsupported in this phase. Tauri packaging, Apple signing/notarization, credentials, deployment, and publishing remain outside Bazel.

## Boundary and non-goals

The initial boundary is deterministic `server-rs` Rust libraries, binaries, tests, and unsigned headless archive inputs. Bazel consumes declared frontend outputs only; it does not run Vite, JavaScript tests, or Playwright. It does not package Tauri, sign artifacts, access credentials, deploy, or publish. `docs/DECISIONS.md` records the conditional hybrid decision; Bazel is not authoritative and Cargo/pnpm direct workflows must remain usable.

## Target conventions

Use package-local, descriptive `snake_case` labels. Public library/binary/archive interfaces use `//visibility:public`; build helpers and generated intermediates are private. `rust_library`, `rust_binary`, and `rust_test` declare every `srcs`, `deps`, and runtime `data`; `sh_test` declares scripts and executable/data labels. Keep targets near their sources and avoid `//...` dependencies that invalidate the whole repository. Use `small` for static checks, `moderate` for Rust integration tests, and `large` only for archive/integration work. Tests should use `manual` only for provider- or credential-dependent workflows; the path-stability test is always selected. Platform constraints must be explicit when a target is not host-independent.

Generated files are declared outputs, never source-discovered from the checkout. Prefer label-derived `$(location)`/`$(rootpaths)` values. The existing `CARGO_MANIFEST_DIR` workaround uses runtime data overrides such as `PANTOKEN_CORPUS_FILES` and `PANTOKEN_CLIENT_DIST`; these values must be declared and must not contain checkout, sandbox, temp, `HOME`, or absolute paths in output bytes.

## Lockfiles and dependency updates

`Cargo.toml` and `Cargo.lock` are the Rust dependency source of truth. After a Rust dependency change, run the normal Cargo update/check flow, then `CARGO_BAZEL_REPIN=1 bazel sync --only=crates`; review generated crate-universe/module state and run both Bazel and Cargo gates. `package.json`, workspace manifests, and `pnpm-lock.yaml` are the JavaScript source of truth. Bazel consumes declared frontend outputs and does not resolve pnpm dependencies in this phase.

Review `MODULE.bazel`, `.bazelversion`, and BUILD files separately from application lockfile changes, but use one documented update workflow and a reversible diff. Do not silently replace Cargo or pnpm lockfiles. Generated metadata is either checked in with path/reproducibility checks or intentionally ignored as documented above.

## Hermeticity and path stability

The default `.bazelrc` enables bzlmod, the Bazel-8 `--enable_workspace` repin compatibility, sandboxed actions, strict action environments, and deterministic locale/time settings. No target may inherit ambient environment, credentials, or host paths. Tests that need a home directory set an explicit sandbox-relative `HOME=.` value. Cache reuse is opt-in through `--config=cache` (or a caller-supplied cache directory); missing cache data must never affect correctness.

Run `bazel query //server-rs/...`, `bazel build //server-rs/...`, and `bazel test //:bazel_path_stability_test`. `just bazel-policy-check` performs provider-free static checks. The path-stability fixture compares normalized manifests synthesized under two checkout roots and scans metadata/archive bytes for `HOME`, checkout-root, sandbox, temp, and POSIX/Windows absolute paths. `just bazel-test-allowlisted` requires the exact independently queried server test target set and requires every result to be `PASSED`; there are no allowlisted server test failures. Runtime-spawning tests use declared binary data and `PANTOKEN_SERVER_BIN`, while `server_lib_unit_tests` covers inline Rust tests with explicit dev-dependency labels.

## Ownership

Ownership is package/area based and lightweight: Rust maintainers own `server-rs/**/BUILD.bazel`; release/tooling maintainers own root `BUILD.bazel`, `.bazelrc`, `.bazelversion`, and `MODULE.bazel`; documentation maintainers own this policy. Root/module/toolchain changes require one owner review and one reviewer familiar with Cargo/pnpm boundaries. Keep Bazel changes reversible and update this policy when a supported boundary changes.
